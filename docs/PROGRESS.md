## P2 — схемы документов и валидаторы (2026-11-14)

### Что сделано
- `docai.schemas`: модели `Upd` (статусы 1 и 2), `Bill` (счёт на оплату), `Act`, `Torg12`, `VatInvoice` (счёт-фактура) с общими полями: тип, номер, дата, продавец и покупатель (наименование, ИНН, КПП, адрес), банковские реквизиты продавца (только у счёта, акта и ТОРГ-12), основание (кроме счёта-фактуры), строки и итоги. Деньги — `Decimal`, даты — `date`. `parse_document` выбирает класс по `doc_type`.
- `VatRate`: 0%, 5%, 7%, 10%, 18%, 20%, 22%, «без НДС» и расчётные ставки 5/105, 7/107, 10/110, 18/118, 20/120, 22/122.
- `FIELD_SPEC` (31 поле): путь в схеме, тип значения, вид нормализации, типы документов, где поле есть и где оно обязательно. Тест сверяет его со схемами.
- `docai.validation`: ИНН (10 и 12 цифр), КПП, БИК, ключ расчётного и корр. счёта по БИК, ставка НДС по дате документа, арифметика строк и итогов, заполненность обязательных полей. Каждая проверка возвращает список `ValidationIssue` (код, сообщение на русском, поле, серьёзность) и не бросает исключений.
- Нормализаторы: суммы («12 200,00», «12200.00», «12 200 руб. 00 коп.», «12 200-00»), даты («14.11.2026», «14 ноября 2026 г.», «2026-11-14»), ИНН и КПП с пробелами и подписями, ставки НДС, ОКЕИ, текст и номера документов; `normalize_for_compare` для метрик.

### Проверка
- `uv run pytest`: 329 тестов проходят; `uv run ruff check` — без замечаний.
- Покрытие `docai.validation` — 100% (с ветвлениями): `uv run pytest --cov=docai.validation --cov-report=term-missing`.
- Алгоритмы проверены на публичных реквизитах: ИНН и корр. счета Сбербанка, ТБанка, ВТБ, Альфа-Банка, ЕКС казначейства.

### Ограничения и открытые вопросы
- Ставка НДС проверяется по дате документа (D11). Корректировочные документы, грузоотправитель и грузополучатель, платёжные документы и исправления в схемах пока не описаны.
- Для счёта на оплату, выставленного в 2025 году со ставкой 22%, выдаётся предупреждение, а не ошибка.

## P3 — генератор синтетических данных (2026-11-14)

### Что сделано
- `docai.synth`: справочники (300 организаций, 50 ИП, 24 банка с валидными ИНН, КПП, БИК, корр. и расчётными счетами), каталог из 500 товаров и услуг (канцтовары, стройматериалы, IT-услуги, продукты, транспорт) с кодами ОКЕИ и ценами, генератор документов пяти типов.
- Документ: дата 2025–2026, ставка НДС по дате (20% до 2026 года, 22% с 2026; иногда 10%, «без НДС», 5%, 7%), от 1 до 25 строк, пять форматов номеров («123», «А-0045», «УТ-000123», «123/А», «15/2026»), договор-основание.
- Режим «намеренные ошибки» (5%): неверная сумма строки, НДС строки, итог или ИНН. Пометки лежат в `_manifest.jsonl`, не в разметке.
- CLI: `uv run docai synth generate --n 100 --seed 42 --out data/synth/json` (дополнительно `--error-rate`). Один JSON на документ.
- Новая зависимость: Faker (D14). Решения D14–D17.

- 1000 документов генерируются и записываются за ≈2 с (без учёта запуска Python). Все не испорченные проходят `validate_document` без замечаний, все испорченные дают ошибку. Тест детерминизма проходит.

## P4 — печатные формы (2026-11-14)

### Что сделано
- `docai.render`: 15 шаблонов Jinja2 (УПД, счёт на оплату, акт, ТОРГ-12, счёт-фактура × 3 визуальных варианта; логотип, печать и подпись — заглушки, включаются по seed), рендер в PDF через Chromium (Playwright), текстовый слой настоящий.
- Для каждого PDF — `<имя>.layout.json`: страница и bbox (пункты PDF) каждого напечатанного поля, собранные JS по `data-field`.
- Длинные таблицы: собственная пагинация, шапка таблицы повторяется на каждой странице, строки не режутся.
- CLI: `uv run docai render --in data/synth/json --out data/synth/pdf` (`--seed`, `--variant`, `--limit`, `--stem`).
- Новые зависимости: Jinja2, Playwright, pypdfium2 (D18). Решения D18–D22, источники форм — в DECISIONS.

### Проверка
- `uv run pytest`: 394 теста проходят; `uv run ruff check` — без замечаний.
- Все 1000 синтетических документов отрисованы за ≈100 с: 1141 страница, ни одной ошибки `check_render` (все поля напечатаны, их текст есть в PDF, bbox внутри страницы).
- Для каждого из 15 шаблонов тест проверяет полноту полей; bbox, вырезанный из PDF, содержит напечатанный текст; 40+ строк разносятся на несколько страниц.
- 5 примеров (по одному на тип) и один многостраничный для проверки глазами — `reports/2026-11-14_p4_render_examples/`.

### Ограничения и открытые вопросы
- Формы повторяют структуру граф, но не пиксель в пиксель и не построчно сверены с текстами (D20); счёт-фактура — без граф прослеживаемости и без правок 2026 года.
- Шрифты — системные Windows; на другой ОС вид слегка другой.
- Подписи без ФИО, печати без текста: надписей нет ни в разметке, ни в текстовом слое.
- Блок подписей иногда оказывается один на последней странице (когда не помещается под таблицей).
- Сканы (искажения, шум, поворот) — следующий шаг.

## P5 — «сканы» и фото (2026-11-14)

### Что сделано
- `docai.augment`: растеризация PDF через pypdfium2 в 150, 200 и 300 dpi (массив BGR, без Pillow); три уровня искажения на OpenCV — `clean` (PNG без потерь), `scan` (поворот ±3°, серый фон, размытие, шум, JPEG 70–90), `photo` (перспектива, неравномерный свет, тень, JPEG 50–80). Параметры — в D24.
- Все геометрические преобразования — гомографии; bbox из `<имя>.layout.json` (P4) переводятся в пиксели и переносятся той же матрицей: на выходе `bbox` (охватывающий) и `quad` (точный четырёхугольник), см. D25.
- У результата нет текстового слоя: только JPEG/PNG. Разметка полей лежит рядом: `<имя>_p<стр>_<уровень>_<dpi>dpi.layout.json`.
- CLI: `uv run docai augment --level scan --in data/synth/pdf --out data/synth/scans` (`--level` clean/scan/photo/all, можно повторять; `--dpi` 150/200/300, можно повторять, по умолчанию 200; `--seed`, `--limit`, `--stem`).
- Новая зависимость: opencv-python-headless (D23).
- Примеры: `reports/samples/` — сетки 3×3 `grid_clean|scan|photo.jpg` (одни и те же 9 документов, разрешение 150/200/300 по кругу) и рамки полей поверх трёх картинок на каждый уровень `bbox_<уровень>_*.jpg` (красный — bbox, зелёный — четырёхугольник). Воспроизводятся командой `uv run python reports/samples/make_samples.py`.

### Проверка
- `uv run pytest`, `uv run ruff check` проходят (новые тесты — `tests/test_augment.py`).
- Геометрия: тёмный прямоугольник после warp (поворот, поворот со сдвигом, перспектива) совпадает с перенесённым bbox с точностью ±1 px. Реальные страницы: картинка, развёрнутая обратной матрицей, совпадает с исходной (ZNCC), а со сдвигом на 6 px — заметно хуже.
- Рамки полей проверены глазами на сетках и на `bbox_*`: лежат на полях на всех трёх уровнях и разрешениях.

### Ограничения и открытые вопросы
- Параметры искажений подобраны «на глаз» и не калибровались по реальным сканам и фото; на реальных документах (data/real) их стоит сравнить и при необходимости подправить.
- Не моделируются: перегибы и складки, скрепки, цветные полосы сканера, сильная перспектива (больше 4,5%), обрезка краёв листа. Фон `photo` — искусственная текстура, а не реальный стол.
- bbox многострочных полей (наименование товара в ячейке из двух строк) берётся из разметки P4 как есть; на сетках видно, что у некоторых он тонкий (охватывает первую строку) — это особенность P4, не P5.
- Полный прогон 1000 PDF × 3 уровня × 3 dpi не делался; одна страница при 200 dpi на все три уровня — около 1,3 с.

## P6 — сборка датасета v1 (2026-11-14)

### Что сделано
- `docai.dataset`: `uv run docai dataset build --config configs/dataset_v1.yaml` одной командой генерирует документы, пишет JSON, рисует PDF и делает картинки `clean`/`scan`/`photo` (200 dpi). Растеризация и искажения идут в нескольких процессах (`workers`), результат от их числа не зависит. Конфиг — YAML (`configs/dataset_v1.yaml`), PyYAML добавлен как прямая зависимость (D28).
- Разбиение train/val/test 80/10/10 — **по продавцам** (ИНН), D26: у продавца общие реквизиты, адрес, банк, номенклатура, поэтому при разбиении по документам test «видел» бы тех же продавцов, что и train.

## P10* — постобработка и уверенность (2026-11-16)

### Что сделано
- `docai.postprocess`: после LLM документ нормализуется (ИНН, КПП, БИК, счета, ОКЕИ, пробелы, «№», «ИНН/КПП» в одном поле), проверяется `validate_document`, исправляется там, где ответ однозначен, затем по каждому полю считается уверенность и выставляется статус. Каждое изменение (нормализация и исправление) — запись в `postprocess.corrections`: поле, было, стало, правило, причина (D41).
- Автоисправления — только суммы одной графы (без НДС, НДС, с НДС) и итоги. Условия: единственное значение, при котором строка верна; подтверждение тремя другими числами строки или итогом документа; в тексте-источнике прочитанное значение не напечатано дословно. Количество, цена, ставка НДС, ИНН, КПП, БИК и счета не исправляются (неоднозначно). Для XML из ЭДО исправлений нет.
- Уверенность поля `σ(logit(p₀) + Σ ln LRᵢ)`: исходная вероятность по пути и группе поля, умноженная на отношения правдоподобия четырёх сигналов — проверки (прошла или нет), дословное вхождение в текст (текстовый слой, OCR), совпадение со вторым путём, исправление (потолок 0,85). Каждое слагаемое видно в `fields[].signals` и `reasons`. Формула и все константы — D42.
- Статус: «можно загружать», «нужна проверка» (список `review_fields` по возрастанию уверенности; порог 0,8) или «отклонить» (нет документа или строк, либо уверенность ниже 0,5 у половины полей) — D43.
- Конвейер и CLI: `docai extract` сам запускает постобработку (`result.postprocess`), печатает статус, исправления и поля для проверки; `--cross-check text|vision|ocr` запускает второй путь для сверки. Настройки — блок `postprocess` в `configs/extract.yaml`.
- `docai.eval`: 27 видов намеренных порч (20 «для правил», 7 «вне правил») и измерение доли пойманных (`evaluate_corruptions`) и ложных срабатываний (`evaluate_clean`).

### Проверка
- `uv run pytest` — все тесты проходят (новые: `tests/test_postprocess.py`), `uv run ruff check` и `uv run ruff format --check` чистые.
- Критерии (250 документов датасета v1, сплит test; `reports/2026-11-16_p10_validation/report.md`):

| Критерий | Результат | Порог |
|---|---|---|
| Порчи «для правил» (4302 порчи, 20 видов): замечание проверок | **99,4%** | ≥ 95% |
| Ошибки генератора P3 в датасете (144 документа): замечание проверок | **100%** | ≥ 95% |
| Ложные срабатывания проверок на чистых документах | **0%** (0 из 250) | ≤ 2% |

### Ограничения и открытые вопросы
- **Критерий выполняется для порч «для правил».** Опечатку в наименовании, номер документа, КПП той же формы, дату в пределах года правила не видят (0%). Текстовый слой ловит наименования, адреса, КПП и даты почти всегда, но короткие номера документа и договора — нет: молча загружается 38% порч номера документа и 32% номера договора.
- **Цифра в БИК** ловится на 75% (остальные цифры БИК не входят в расчёт ключей счетов).
- **Проверки не видят согласованной выдумки.** На прогоне P9 vision выдавал строки, прочитанные в другом масштабе, но арифметически согласованные. Поэтому «пройденные» проверки ограничены потолком ×10, а верно ли поле, должны подтверждать текст или второй путь.
- **Настоящие ответы модели (30 документов P9):** верных полей text 94,9%, vision 64,7%, ocr 15,3%. На пути text поля с уверенностью ≥ 0,8 верны в 97%, но только 12% неверных полей получают уверенность < 0,8: большинство ошибок — не опечатки, а расхождения формата с эталоном (адрес без индекса, номер в названии основания, код ОКЕИ, который модель подставила сама). Тип документа (УПД прочитан как счёт-фактура) не проверяется ничем и получает уверенность 0,95 — следующий шаг: признак типа по заголовку в тексте. Словарь «единица измерения ↔ код ОКЕИ» (нужен источник по ОК 015-94) убрал бы основную часть ошибок кодов.
- **Калибровка оптимистична:** исходные вероятности взяты из тех же 30 документов, остальные константы — экспертные оценки. Пересчёт на тестовом сплите — P13. Сверка с ошибающимися путями не бесплатна: у text при сверке с vision и ocr на проверку уходит больше документов («можно загружать» 4 → 2 из 10), зато доля пойманных неверных полей растёт с 12% до 29%.
- Автоисправление никогда не срабатывает, если текст-источник содержит исходное значение: документ с настоящей ошибкой (как у генератора P3) уходит на проверку, а не «лечится». Из 144 документов P3 исправлено 2.
- Сверка (`--cross-check`) удваивает время обработки (документ 1–6 минут).

### Задачи на потом (найдено при P10)

## P11* — методика оценки (2026-11-16 – 2026-11-17)

### Что сделано
- `docai.eval`: сравнение ответа с эталоном по FIELD_SPEC после нормализации (`compare.py`, D44). Поля шапки — accuracy и доля выдумок, текстовые поля — ещё ANLS (τ = 0,5); строки таблицы сопоставляются венгерским алгоритмом (`assign.py`, своя реализация, проверена перебором) по сходству строк, отсюда precision/recall/F1 по строкам (найдена пара и верна целиком) и по ячейкам; документ «можно загружать без правок» — ни одной ошибки в обязательных полях.
- Калибровка уверенности P10 (`calibration.py`): ECE и MCE (10 корзин), Brier, AUROC, таблица корзин и график надёжности `reliability.svg`. Производительность: секунд на страницу, пиковая VRAM, токены.
- Статистика (`stats.py`, D45): 95% интервалы кластерным бутстрепом по документам (2000 повторов, seed из конфига) для всех основных метрик, по типам документов, уровням качества и путям; парный бутстреп разности и тест Макнемара — для сравнения конфигураций на одних и тех же документах (в том числе ответ модели до и после постобработки).
- Прогон (`predict.py`, `run.py`, D46): `extract` разделён на `extract_raw` и `finish`; «сырые» ответы модели кэшируются с отпечатком конфига в `data/experiments/eval/<имя>/`, постобработка применяется при подсчёте — константы P10 пересчитываются без нового прогона модели. Прерванный прогон продолжается.
- Отчёт (`report.py`): `reports/<дата>_<имя>/` — `metrics.json` (все метрики с интервалами и счётчики по документам для парных сравнений), `report.md`, `config.yaml`, `reliability.svg`, 5 худших примеров с картинкой и таблицей расхождений, `notes.md` с наблюдениями вручную. Реальные документы — только с псевдонимами и обезличенными значениями, без картинок.
- CLI: `uv run docai eval --config configs/eval/<имя>.yaml [--predict-only]`, `uv run docai eval-compare A/metrics.json B/metrics.json`. Конфиг задаёт модель, путь, версии промптов, выборку (стратифицирована по типу, уровни по кругу или все), исключённые документы, seed. Шаблон записи эксперимента — `docs/EXPERIMENTS.md`.

### Ограничения и открытые вопросы
- **Ответ модели не воспроизводится** при temperature 0 и seed 42: из 19 повторов 12 отличаются (средний |ΔF1| документа 4,1 п.п., максимум 22 п.п.; статус «без правок» не изменился ни разу). - Прогон шёл частично от батареи и через сон: 19 таких документов переделаны на сети (журнал Windows Kernel-Power), у одного 13 с из 255 на батарее — оставлен. Подробности — `notes.md` отчёта.

### Эксперимент: даты «как напечатаны» (2026-11-17, D47)
- Причина провала базы — схема черновика: `format: date` в JSON Schema заставлял модель писать ГГГГ-ММ-ДД, и она переписывала туда цифры ДД.ММ.ГГГГ. Сделано: `date_format` в конфиге извлечения (`iso` | `printed`), при `printed` дата — свободная строка, её разбирает `parse_date`; промпты `text_v2`/`vision_v2` отличаются от v1 одной строкой о датах (тест следит). База P11 закреплена явным `date_format: iso`, её кэш годен (поле со значением iso не входит в отпечаток).
- Защита питания для прогонов (`power_guard`): прогон ждёт зарядку и пересчитывает документ, во время которого был переход на батарею или сон. Исключение «модель зациклилась» (Ollama прервала генерацию) кэшируется как несобранный документ, чтобы пересборка отчёта не меняла метрики; время постобработки исключено из метрики скорости — две пересборки отчёта подряд дают побайтно одинаковые `metrics.json` и `report.md`.
- Результат на тех же 100 документах (`configs/eval/p11_date_printed.yaml`, отчёт `reports/2026-11-17_p11_date_printed/`, парное сравнение с базой):
