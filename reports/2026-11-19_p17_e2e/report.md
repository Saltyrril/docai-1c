# P17 — сквозной сценарий и замер цикла «файл → документ в 1С» (2026-11-19)

Железо: Ryzen 5 5600H, RTX 3050 Laptop 4 ГБ, модель `qwen3.5:2b-q4_K_M`. Документы синтетические.
Сырые данные: `api_run.json` (10 документов через API), `1c_logs/*.out` (отчёты автопроверки 1С с метками времени).

## 1. Десять демо-документов через API (`scripts/demo_e2e.ps1`)

Скрипт сам поднял сервис (Ollama уже работала), проверил `/v1/health`, прогнал набор и остановил то, что запустил.

| 01 УПД из ЭДО | xml | upd | upload | 0 из 42 | 1,1 |
| 02 УПД из ЭДО (услуги) | xml | upd | upload | 0 из 42 | 1,0 |
| 03 счёт PDF | text | bill | review | 4 из 39 | 14,1 |
| 04 УПД PDF | text | upd | upload | 0 из 24 | 8,1 |
| 05 счёт PDF | text | bill | upload | 0 из 39 | 11,2 |
| 06 счёт, чистая картинка | vision | bill | review | 55 из 146 | 45,8 |
| 07 УПД, чистая картинка | vision | **bill (ошибка: это УПД)** | review | 16 из 30 | 12,3 |
| 08 счёт, скан | vision | bill | review | 13 из 36 | 19,5 |

Итого 10 из 10 обработаны, сумма 147 с, медиана 13,3 с, максимум 45,8 с. Статусы: `upload` — 4, `review` — 6.
Замечание: документ 07 (УПД) модель назвала счётом — это реальная ошибка пути vision, на защите её лучше не показывать, либо показать как случай «человек исправил вид».

## 2. Время на документ: без человека и с проверкой

**Измерено (машинная часть).** Секунды от старта автопроверки 1С (отправка файла) до готового состояния, по меткам времени в отчётах 1С:

| Путь | Распознавание готово, с | Форма проверки открыта и правки ушли в сервис, с | Документ создан в 1С, с |
|---|---|---|---|
| XML из ЭДО (`xml_create.out`) | 3,5 | 7,2 — это и есть конец цикла | **7,2** |
| PDF с текстом, счёт (`pdf.out`) | 15,8 | 16,8 | нужен человек (см. ниже) |
| Скан УПД, vision (`scan.out`) | 12,6 | 13,7 | нужен человек |

- **Без участия человека** полный цикл «файл → непроведённое поступление + счёт-фактура в 1С» замерен только для XML из ЭДО (справочники совпали точно): **7,2 с**. Опрос заданий идёт раз в 2 с, поэтому цифра округлена вверх примерно на секунду-две.
- Для PDF и сканов без человека в нашей базе цикл не замкнуть: у них статус `review` (красные поля, например КПП), а контрагента, договора и номенклатуры в демо-базе нет. Машинная часть (распознавание + открытие формы) — 13–17 с, создание документа в 1С после подтверждения — порядка 4 с (по XML: 7,2 − 3,5 с).
- Когда справочники совпали не точно, автопроверка не создаёт документ и честно останавливается: см. `xml_similar_item.out` («Строка 2: не выбрана номенклатура» — «Онлайн касса Эвотор 7.2» лишь похожа на «Онлайн-касса»).

**Не измерено — время человека.** Я не могу засечь живого человека, поэтому в отчёте только оценка по числу полей, которые форма подсвечивает. Принятые допущения (их надо проверить секундомером, таблица ниже): 20 с на просмотр страницы, 5 с на каждую жёлтую или красную ячейку, 40 с на создание отсутствующего контрагента, договора или номенклатуры через форму.

| Документ | Машина | Проверка (оценка) | Итого (оценка) |
|---|---|---|---|
| УПД из ЭДО, всё найдено | 7 с | 10 с (просто посмотреть и нажать) | около 20 с |
| PDF-счёт, 4 красных, контрагент и договор новые | 17 + 4 с | 20 + 4×5 + 2×40 = 120 с | около 2,5 мин |
| Скан УПД, 11 жёлтых/красных, поставщик новый | 14 + 4 с | 20 + 11×5 + 3×40 = 195 с | около 3,5 мин |

Для сравнения ручной ввод такого документа с тремя строками — порядка 3–5 минут (оценка, не измерение); выигрыш честно виден на документах из ЭДО и на повторных поставщиках, когда справочники уже заполнены.

## 3. Устойчивость: сервис или Ollama недоступны

Проверено настоящей 1С на копии демо-базы (`1c_logs/service_down.out`, `ollama_down.out`) и по снимкам формы.

| Сценарий | Что показала 1С | Падение |
|---|---|---|
| Сервис не запущен (порт без сервиса) | Строка «Сервис»: «Сервис docai не отвечает по адресу http://127.0.0.1:8012. Запущен ли он? В PowerShell из папки проекта: .\scripts\start.ps1»; файл в списке — «Не отправлен» с той же причиной; счётчик «ошибок: 1» | нет, 1С закрылась штатно |
| Сервис жив, Ollama нет (скан) | Шапка: «работает не полностью: Ollama недоступна… PDF без текста и сканы не распознаются, XML из ЭДО — да»; строка задания — «Ошибка распознавания» + «Ollama недоступна по адресу … Запустите: ollama serve» | нет |
| Сервис жив, Ollama нет (XML) | XML обрабатывается (2 из 2, 1–2 с): модель не нужна | нет |
| Форма проверки открыта при недоступном сервисе | В шапке причина, картинки нет; | нет |

Найдено и исправлено при проверке:
- При недоступном сервисе в форме проверки оставались активными «Готово» и «Создать документ в 1С». «Готово» отправило бы пустые значения и затёрло ранее сохранённые правки. Теперь кнопки отключаются, форма закрывается крестиком (тест `test_review_form_disables_buttons_when_service_gave_no_data`).
- Если на порту отвечает не сервис (HTML, другая версия), разбор JSON бросал исключение и 1С показывала диалог об ошибке платформы. Теперь четыре места разбора ответа под `Попытка`, сообщение «По адресу … отвечает не сервис docai» (тест `test_service_answers_are_parsed_under_try`).

Не проверено: сервис упал в середине обработки при открытой форме списка (опрос продолжается раз в 2 с и показывает причину в «Замечаниях», это видно по коду, но живьём не гонялось); зависание сервиса без закрытия порта (таймаут запроса 30 с блокирует форму на это время).
